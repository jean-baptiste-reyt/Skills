# Design Split — playbook

## Planning

1. Diff the source branch (or its uncommitted working tree) against its real current base — `git merge-base`, not a remembered or stale idea of the base tip.
2. List every changed file with its line count. Group along real seams: pure logic/types with no rendering (testable standalone) is the earliest slice whenever it exists — lowest-risk, fastest to review, needs no visual check at all. A presentational component with its own Storybook story comes next. Page/route composition — hooks, real data, wiring — comes last.
3. Size to the actual content, not a fixed target. A ~150-line component doesn't need three PRs to be reviewable; a genuinely large page might need five. If everything already fits comfortably in one PR a developer could review in one sitting, say so and don't force a split for its own sake.
4. Default every slice to independently mergeable. Stack two slices only when one's code literally can't compile or run without the other already existing (a real import dependency) — not because they're thematically related.
5. i18n ships inside whichever slice introduces the string, in every locale the project supports — never a separate "add translations later" slice.
6. Exclude anything that isn't this feature's own work. A stray local/generated file (e.g. a dev-server-regenerated block appended to a coding-standards doc) doesn't belong in any slice, even if it shows up in the working tree diff.
7. When a size call is genuinely ambiguous, judge it against `[your-task-scoping-skill]`'s "splitting work into multiple tickets" rubric, if it has one (vertical slice, testability, reviewability, ordering) instead of guessing — no slice should be a "puzzle piece" with no standalone value, and each one needs something independently verifiable.

## Execution

**Step 0, once, before any slice:** inspect every change that would enter the snapshot — review `git diff`, `git diff --cached`, and the contents of each untracked file from `git status`. Exclude anything that looks like a secret, credential, personal data, or an unrelated file; never a blanket add-everything. If an excluded item looks like it might actually be needed for the feature, stop and ask how to replace it safely — never push sensitive data regardless. Commit the remaining current state (including safe uncommitted work) onto a dedicated snapshot branch, and push it. Never open a PR from it, never merge it. This is the safety net — exploratory work that only ever existed as uncommitted changes has been lost this way before — and it's the reference every slice's rewritten UI gets diffed against in step 5 below.

Per slice, in dependency order:

1. Create the branch from the real base tip (not from a previous slice's working state, unless this slice is deliberately stacked on that one). Isolate the work in its own git worktree so parallel slice work doesn't collide on one working directory.
2. Isolate just this slice's files/hunks — don't carry over a later slice's code even if it's sitting in the same working tree today.
3. Rewrite via a subagent for coding-standards compliance (destructured params, no unjustified type casts, named constants, functional style, real tests — whatever your own project's `AGENTS.md`/equivalent actually requires). State the hard constraint explicitly in the subagent's brief: implementation can change freely, rendered output cannot, beyond aligning to a real shared component. For any UI component, run `[your-design-system-review-skill]` (picker mode) before deciding whether to keep the original's approach. State explicitly, every time: every piece of data it touches or adds (a test fixture, a Storybook story, an example value) must come from a real, existing source in this repo — if it can't find one, it must say so in its report rather than invent a plausible-looking placeholder. For a backend slice, also brief it on your task-implementation skill's "coding rules" and "domain invariants" sections, if it has them (ORM footguns, custom ID-type conversions, multi-tenant/sub-account scoping — whatever your own backend's known gotchas are), and have it regenerate migrations via `[your-db-migration-skill]` instead of keeping any hand-edited migration from the original branch. Close the step by having the same subagent run `/[your-coding-rules-skill]` on its own diff, while it still holds full session context of what it wrote.
4. **Never trust a subagent's self-report at face value.** Read its actual diff yourself, line by line, before moving on — not just its summary. For any specific, checkable claim it makes (a call-site count, "this file doesn't exist," "this state is reachable," any fixture/example data it added), independently re-derive it yourself (grep, read the real source file) rather than accepting its word. This applies hardest to invented-looking example data — cross-check every id, title, URL, and field against the actual catalog/data file, not the subagent's paraphrase of it. A subagent has fabricated fictional example data before this rule was added — this step exists because of a real incident, not as a precaution against a hypothetical.
5. Run the project's real checks for the package touched — lint, type-check, unit tests (see your own `[your-frontend-dev-skill]`/`[your-frontend-test-skill]`, or the backend equivalents).
6. If the slice has any visual surface: launch the app and screenshot the affected screen(s) on both the snapshot branch (step 0) and this cleaned-up branch, and diff them — drive the browser tools directly rather than through a generic app-launcher skill (see `SKILL.md`). A difference that comes from correctly aligning to the real design system is not a blocker — confirm it's actually that, then note it in the PR description rather than reverting it; a difference from anything else is a blocker: fix it or revert that specific change, don't ship it silently. Then spawn a second, fresh subagent with no context on why the implementation looks the way it does — hand it only the touched components and `[your-design-system-review-skill]`'s Reviewer-mode instructions, so its design-system-compliance check isn't anchored by the rewrite subagent's own reasoning.
7. Review the slice's diff — correctness, reuse, simplification, stale comments left over from earlier design iterations. Invoke `code-review`/`simplify` if useful, and check it directly against your project's own coding-standards doc (`AGENTS.md` or equivalent, including any package-specific version and the backend equivalent) either way — a generic skill's pass doesn't know this repo's own rules.
8. Commit, push, open a draft PR — target the real base branch for an independent slice, or the immediate dependency's branch for a stacked slice (retarget it at the real base once that dependency merges, so the diff never balloons to include already-merged work). Description covers: what changed, why it's this size, which slice(s) it depends on (if stacked), and closes with a line telling the reviewer to run `/[your-coding-rules-skill]` themselves before merging — an independent pass on top of the one the rewrite subagent already ran on itself in step 3.

## The QA branch, when one is actually needed

Build it only per the `SKILL.md` rule. When needed: branch from the real base, merge every slice branch into it in dependency order, push, and never open a PR from it — it exists purely so someone can preview the whole feature running in one app before every slice has individually merged. Rebuild it (force-push after re-merging) whenever any slice branch changes.
